To the story of the cve-patch-checker

The cve-patch-checker

  • local application for checking security related submissions

steps:

  • ABI check resulting binary against code stream
  • lint the submission
  • rebuild with & without patch ⇒ compare binaries (i.e. did the patch actually change a thing?)
  • code stream check: check if submission needs to be done against other code streams too, apply it and restart checks there too

But it had problems

  • bad connection ⇒ checks take ages/stall
  • rebuilds resource intensive

What if we made it scalable?

  • internal k8s cluster became available, would be hosted, can run plethora of workloads there
  • checks could run there, geographically close to the "main" repos with tons of compute at their disposal
  • offload the expensive work to cluster, scale up whenever need arises and scale down again

decision early: move to microservices, would allows independent deployments & scaling made sense: multiple distinct and independent components

🤔 we have a Kubernetes cluster at our disposal

  • run checks concurrently
  • scale on demand

Microservices it is!

Architecture

  • orchestrator receives task from user ⇒ enqueue via celery, tell collector
  • collector stores task in DB, collects results from workers, handles new task creation
  • workers take tasks from queue, report results back to celery and via REST to collector
  • collector stores result in DB, streams results back to user
  • also present: general cache for data, s3 for storing bigger data chunks, Redis cache

looks quite nice on paper:

  • textbook cloud native architecture, with the default components
  • could scale & deploy everything as we like it, checks would no longer hog your box

It looked perfect

  • "textbook" architecture wasn't so good in production
  • users submitted a task for a CVE submission ⇒ never finished or disappeared

And then we deployed it 🫠

  • checks disappeared
  • system stopped responding
  • task multiplied uncontrollably

Hey where did my job go?

  • users frequently encountered disappearing jobs
  • problem: one of the subtasks would die for $reasons, but it didn't get auto-resumed
  • even worse, it couldn't be: celery had the parameters, postgres didn't

Two sources of truth

  • celery gets all args + job ids, DB only receives job IDs + task types
  • primary reason: DB only stores data for web response and not to tie schema

Retry is not the same as resume

  • PostgreSQL knew the run existed + initial params (and even that not initially)
  • sub-task inputs lived only in Celery messages, failure there must be retried
  • restarting could not reconstruct the intended work

How do you debug this?

  • debugging sucked hard, because there was only kubectl logs
  • reconstruct full run next to impossible: query DB for task IDs, kubectl logs ⇒ grep for IDs ⇒ kubectl logs again, etc.pp.
  • fun problem: when containers die, you loose the logs and are screwed
  • so you just have logs, but connecting all the dots is manual, especially if things go south
  • do mind: as DB != celery, so only because DB says so, doesn't mean the task actually exists in Celery and vice versa

OpenTelemetry to the rescue?

  • oTel trace: whole distributed operation span: a single event in the operation
  • span supports parent spans, belongs to trace
  • supports auto-instrumentation (easy to get started with)
  • caveat: your traces shouldn't grow to a too large size ⇒ instrumentation will die then

⇒ trace connects API request to Celery msg, worker task, DB request

  • also support attaching trace & span to log events, exceptions, etc.
  • Metrics: something is wrong
  • Traces: where did it come from?
  • Logs: what happened there?

but observability ≠ reliability

  • on one horrific day, the queue exploded

Distributed systems are hard

  • in a distributed system, every component can fail :-(

Pods Are Disposable

  • k8s can kill anything at any moment in time and the app must survive that

k8s can stop your pod at any moment

But the tests are green!

  • most testing done in docker compose ⇒ checks happy path by default, very little failure path testing

Test for the unhappy path too!

How do we stop losing & duplicating jobs?

problem: crash of any component in the "outbox" causes two sources of truth to diverge even worse: cancellation becomes a nightmare

Define Errors Out Of Existence

  • quote from Chapter 10, A Philosophy of Software Design by John Ousterhout
  • if you can avoid an error from happening, do that
  • simple example: unset needn't throw when variable not set more complex:
    • contracts in Ada/Rust ⇒ prevent "bad stuff" at compile time
    • idempotency: resubmit task not error but just get old result back

If you can avoid a failure situation, do that! 

# error or not?
unset foo

Merging the backends

  • hindsight is always 20/20: why two backends when one removes HTTP?

Remember the two backends?

Transactional outbox

  • in a single transaction, commit the new task state and an outbox entry
  • an independent dispatcher publishes outbox entries to RabbitMQ
  • if publication fails it retries
  • if the dispatcher crashes after publication but before marking success, the task may be published twice ⇒ idempotency crucial
  • outbox fixes dual write or task loss, not duplicate processing ⇒ need not to duplicate work

Remember the two sources of truth?

And the fan out?

  • big issue: task creation happens during work

Lessons learned

  • distributed systems are unforgiving and will punish your mistakes in the worst way (especially if their infra is flaky)
  • you most likely can solve your problem with a bigger machine and off the shelf solutions
